# Альфа: ручной деплой и обновления

В `main` используется «Атлас» на компьютере и «Очаг» на телефоне. Нужен Node.js 24+. Локальный запуск: `start-firewell.cmd` или `bash start-firewell.sh`. Обычный запуск сохраняет аккаунты и матчи в существующей SQLite. `start-firewell-clean.cmd` предназначен только для сознательного сброса локальной игры.

## Railway

1. В своём существующем сервисе выбери репозиторий `LuwnFM/CCGame`, ветку `main`, и вручную запусти деплой. В репозитории есть Dockerfile; он запускает сервер и весь веб-интерфейс вместе, без отдельного Vercel-клиента.
2. Подключи постоянный Volume к `/data`. Задай `FIREWELL_DB=/data/firewell.sqlite`. Если у сервиса уже есть база на другом Volume, используй её прежний путь либо перенеси её при остановленном сервере. Новый пустой Volume создаст отдельную новую базу, старые аккаунты сами в неё не попадут.
3. В серверных Variables задай `FIREWELL_ALPHA_PASSWORD` — свой общий пароль регистрации длиной не менее 10 символов. Не добавляй его в GitHub. `FIREWELL_BIND=0.0.0.0` уже задан в Dockerfile. `PORT` читается из окружения Railway; без него используется 3000.
4. Оставь одну реплику: SQLite и состояние матчей рассчитаны на один сервер. Не запускай команды очистки базы при сборке или старте. Для единого адреса игры `FIREWELL_CLIENT_ORIGIN` не требуется.
5. Открой публичный HTTPS-домен сервиса. `/api/health` должен вернуть `{"ok":true,"service":"firewell-ccg"}`. Зарегистрируй тестовый профиль, начни матч с ботом, обнови страницу и проверь возврат в тот же профиль/матч. Затем сделай повторный деплой и повтори вход: проверяется сохранность Volume.

Для будущих обновлений при включённом в Railway автодеплое достаточно обычного push в `main`; иначе выполняй ручной Deploy из `main`. Сохраняй тот же Volume и путь базы. Репозиторий сам не включает автодеплой и не меняет настройки Railway/Vercel. Перед обновлениями храни резервную копию базы: копируй SQLite при остановленном сервере или средствами SQLite backup (обычная копия активного файла без WAL может быть неполной).

После повторного подключения GitHub-интеграции проверь новый push: в Railway должен появиться деплой с SHA нового коммита из `main`. Успешный push и зелёные проверки GitHub сами по себе не подтверждают успешный запуск Railway. Если сервис ограничивает запускающие деплой пути (Watch Paths), изменение одной документации может не вызвать сборку.

## Проверки разработчика

- `npm test` — быстрые проверки движка, сервера, оплаты, сдачи и настроек редактора.
- `npm install --no-save playwright@1.57.0 && npx playwright install chromium` — только для браузерных тестов, игре установка пакетов не нужна.
- `node --experimental-strip-types test/browser-e2e.mjs` — два браузерных игрока, PvP, чат, колоды, защита и Легенды.
- `npm run test:dialogs` — формы профиля, отмена и подтверждение игровых действий, возврат из сброса, уникальные награды и мобильные окна на трёх размерах экрана.
- `node --experimental-strip-types test/browser-bot-release.mjs` — шесть реальных матчей с серверным ботом, обе адаптивные темы, завершение матчей и снимки экрана. Тестовый игрок выбирает действия через ограниченную стратегию бота и отправляет их через HTTP из браузера; это не ручное нажатие каждого хода. Все аккаунты и SQLite временные.

Tinyfish может проверить публичный адрес после твоего ручного деплоя. Локальный адрес тестового сервера ему недоступен; локальный Playwright-прогон не выдаётся за Tinyfish-проверку.
