# Firewell CCG · Модульная система механик (0.9.15-alpha)

**Источник истины:** текущая ветка `codex/unified-events-zones-registry`, PR #5. Правила и сохранённая версия `0.9.13-alpha` не переписываются. Новые карты — сериализуемые данные в `src/cards/<цвет>/<тип>/<card-id>.ts`.

## Где живёт логика

| Слой | Модуль | Назначение |
|---|---|---|
| Транзакционное ядро | `src/core.ts` | порядок игроков, ревизия, идемпотентность, клон состояния, откат и лимит операций |
| Команды | `mechanics/commands/{setup,battlefield,techniques,legends,rituals,combat}.ts` | все 16 зарегистрированных команд; добавление команды без изменения ядра |
| Контракты | `mechanics/{command-contracts,effect-contracts}.ts` | расширение TypeScript-интерфейсов через declaration merging |
| Призыв и зоны | `mechanics/zones.ts` | один `summon`, размещение, Сброс, стирание, перемещения, добор |
| События | `mechanics/events.ts` | FIFO события, предел цикла, события входа, гибели, начала хода и перемещений |
| Эффекты | `mechanics/effects/<kind>.ts` | **18 файлов** независимых активных механик с регистрацией `registerEffect` |
| Пассивные свойства | `mechanics/traits/<kind>.ts` | **15 файлов** объявленных свойств, подавляемых Немотой и Стазисом |
| Бой | `mechanics/combat.ts`, `combat-hooks.ts` | общие пакеты урона и подключаемые боевые хуки |
| Текущие статусы | `mechanics/statuses.ts` | тики Отравы с учётом Стазиса |
| Смерть | `mechanics/death-queue.ts` | очередь Последнего слова; фактические эффекты зарегистрированы отдельно |
| Ритуалы | `src/ritual.ts` + `commands/rituals.ts` | условие Жертвы, выбор жертв и наград |

### Активные механики (каждая имеет файл `effects/`)

`healRuler`, `draw`, `summon`, `summonSkeleton`, `summonBonePair`, `stunEnemy`, `stasisEnemy`, `damageOpponent`, `reanimate`, `cleanse`, `ward`, `silence`, `bind`, `recoverCreature`, `summonSignature`, `raiseSacrifice`, `damageController`, `damageAllCreatures`.

Исторические `summonSkeleton`, `summonBonePair`, `summonSignature`, `raiseSacrifice` сохранены как адаптеры; **в новых картах используйте `summon` с `cards:[...]`**.

**Важно: `ward` («Оберег») зарегистрирован, но пока намеренно выбрасывает ошибку «Оберег ещё не реализован»; его нельзя отмечать как рабочую игровую механику или выпускать в картах.** Это отдельная незакрытая задача правил.

### Пассивные механики (каждая имеет файл `traits/`)

`guard` (Страж), `flying` (Полёт), `firstStrike` (Первый удар), `piercing` (Пробивание), `lifesteal` (Похищение жизни), `haste` (Мгновенная атака), `zeal` (Рвение), `extraAttacks` (Ещё удар!), `stealth` (Скрытность), `poisonHit` (Отрава), `shield` (Щит), `majestic` (Величественный), `cannotAttack` (не может атаковать), `sacrifice` (Жертва), `auraAttack` (аура атаки).

Некоторые свойства (например, `sacrifice` или `majestic`) читаются в правилах Ритуала/замены зон, а не как отдельные боевые пакеты; их **декларации** независимы, но подробные правила соответствующих действий остаются в специализированных модулях Ритуала/зон. Это целевое разделение: не создавать новую функцию под конкретную карту.

## Как добавить карту с существующей механикой

Создайте `src/cards/<цвет>/<тип>/<id>.ts` с сериализуемым объектом `Card`, укажите, например, `firstStrike:true` и/или `onEntry:{kind:'summon',cards:[...]}`. Добавьте импорт и число копий в `src/cards/<цвет>/index.ts`. **Не трогайте `core.ts` или обработчик каждой карты.** Используйте стабильный ID и тест каталога.

## Как создать новую механику

1. Для **событийного эффекта** расширьте соответствующий интерфейс `EntryEffectSpecs`, `TechniqueEffectSpecs`, `LoyaltyEffectSpecs` или `DeathEffectSpecs` в отдельном файле и зарегистрируйте обработчик через `registerEffect(channel,kind,handler)`. Добавьте статический импорт модуля в `src/mechanics/effects/index.ts` или `plugins/index.ts`. Данные эффекта хранятся только в карте.
2. Для **свойства** расширьте `Card`, добавьте `traits/newTrait.ts` с `registerTrait` и импортируйте его из `traits/index.ts`; затем подключите влияние к нужной фазе через боевой хук или модуль команд, не меняя ядро.
3. Для **новой команды** расширьте `CommandPayloads`, зарегистрируйте её в отдельном модуле `commands/` через `registerCommand`; ядро автоматически применяет базовую проверку хода, ревизию, ключ и атомарный откат.
4. Для **нового события/боевого правила** используйте `onGameEvent` или `registerCombatHook`; регистрации возвращают функцию отключения для тестов.
5. Протестируйте позитивный сценарий, неправильную цель, исключения по фазе, подавление эффектов, зоны 8+4, цепочки гибели и лимит операций. Проводите не менее 288 симуляций на всех шести цветах и Chromium PvP E2E.

**Безопасность:** обработчики пишутся только в исходниках доверенного репозитория. Никакого `eval`, запуска JavaScript из пользовательских карт, динамической загрузки сторонних сценариев или неподтверждённых эффектов.

## Регрессионные проверки

`test/mechanics-modularity.test.ts` проверяет, что все свойства и эффекты карт реально зарегистрированы. `test/engine-extensibility.test.ts` создаёт новые команду, эффект и свойство без изменения ядра. `test/events-zones-registry.test.ts` проверяет переносы, очередь событий, смерть и атомарный откат. Полный `npm test` проверяет симуляции колод, а GitHub CI дополнительно запускает Chromium E2E.

Открытые вопросы перед следующими картами: определение точной семантики Оберега и новых механик, расширение UI для их понятного текстового описания и отображения, версионирование правил для несовместимых изменений сохранений.
