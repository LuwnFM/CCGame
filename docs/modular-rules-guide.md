# Система модульных игровых правил Firewell CCG

**Основной принцип:** один исполняемый источник для каждой проверки, одна реализация у каждой механики, единый реестр взаимодействий. Никаких дополнительных исполняемых правил в документах или фронтенде.

## Где менять правила

| Цель изменения | Единственное основное место |
|---|---|
| Поведение отдельного ключевого слова (Немота/Страж/Не может атаковать/Величественный и др.) | \`src/mechanics/traits/<trait>.ts\` |
| Поведение отдельной Техники, эффекта Вступления, Последнего слова, Лояльности | \`src/mechanics/effects/<effect>.ts\` |
| Допустимость вручную выбранной цели | \`src/mechanics/rules/targets.ts\` с предикатом \`traits/majestic.ts\` |
| Готовность атакующего и перехватчика | \`src/mechanics/rules/combat-eligibility.ts\` |
| Подавление зарегистрированных свойств Немотой и Стазисом | \`src/mechanics/rules/suppression.ts\` → \`trait-registry.ts\` |
| Вытеснение, дубликаты имён и Уникальность | \`src/mechanics/rules/placement.ts\`; действия удаления/замены остаются в \`commands/battlefield.ts\`, \`commands/rituals.ts\` |
| Целые количества, игровые ошибки | \`src/mechanics/rules/validation.ts\` |
| Обычный/массовый урон, фазы боя, нанесение Отравы | \`src/mechanics/combat.ts\`, \`effects/damageAllCreatures.ts\` |
| Тики Отравы, завершение эффектов и статусные часы | \`src/mechanics/statuses.ts\`, \`commands/setup.ts\` |
| Очередь эффектов гибели / Вступления | \`death-queue.ts\`, \`events.ts\` |
| Разрешённая оплата | \`src/mechanics/energy.ts\` (уже общая система) |
| Машинно-читаемая матрица всех механик и статусов | **\`docs/mechanics-registry.json\`** — добавить \`interactionPolicy\`, \`statusPolicies\`, \`crossRules\` |
| Регрессионные проверки | \`test/mechanics-rules-contract.test.ts\`, \`test/mechanics-interactions-20261023.test.ts\`, функциональные тесты карточек |

## При создании механики

1. Добавить изолированный \`traits/<name>.ts\` либо \`effects/<kind>.ts\`, зарегистрировать через соответствующий \`index.ts\`. Карта только декларативно ссылается на эту механику.
2. Специфику поместить в обработчик механики. Если нужна уже существующая проверка (цель, готовность, оплата, подавление) — переиспользовать её из \`rules/\`, не копировать.
3. Заполнить **существующий** \`docs/mechanics-registry.json\`. Не заводить второй список зарегистрированных механик. Указать владельца кода, взаимодействия, допустимую цель, suppressible / поведение, тесты.
4. Добавить тест механики и тест её взаимодействия с затрагиваемыми статусами. Выполнить \`npm test\`, затем браузерные, PostgreSQL и replay/regression.
5. На UI не дублировать авторитетную валидацию: интерфейс лишь показывает допустимые варианты; сервер повторно проверяет их для каждого действия.
6. Не объявлять запланированные эффекты работающими: настоящий Оберег, Предвидение, Рикошет, Детонация, Магомутация, Отклик Владения и случайный урон как отдельная карта ещё не имеют готовых обработчиков.

## Важные решения

- **Немота + Не может атаковать:** Немота подавляет это свойство, и готовое Существо вправе атаковать. Но Стазис сам по себе запрещает действия.
- **Величественный:** запрет **ручного** выбора цели техникой/способностью; автоматический случайный, глобальный урон и атаки работают; печатная защита от вытеснения сохраняется.
- **Щит + Отрава при попадании:** эффект попадания требует нанесения боевого урона. Стазис останавливает будущие тики Отравы.
- **Печать на карте vs состояние:** \`Card\` содержит данные и свойства, \`Permanent\` содержит повреждения и статусы; без явной миграции не менять формат хранимого матча.
- **Правила не находятся в одном гигантском файле:** папка \`rules/\` обеспечивает повторное использование, а конкретный модуль механики отвечает за свою реализацию.
- **Матрица документирует текущую архитектуру**, но не является исполняемым DSL; такое изменение потребовало бы миграции и долгого аудита. По умолчанию новые механики добавляются без изменения \`core.ts\`.

## Автоматическая защита от регрессий

\`test/mechanics-rules-contract.test.ts\` сверяет каждый trait/effect с единым реестром, реальность путей файлов, матрицу статусов, ID связей и то, что в эффектах не появилось новых копий общих проверок. Функциональные тесты проверяют допустимость целей, Немоту, боевые ограничения, Уникальность и механики Существ. Историческая матрица из 324 сценариев всё ещё требует отдельного полного нормативного аудита: этот документ не означает 324 прошедших теста.

## Совместимость

\`RULES_VERSION\`, структура \`Game/Card/Permanent\`, IDs, исходные карты, цена/энергия, порядок событий, логи матчей и SQLite/PostgreSQL не меняются. Запущенные комнаты остаются на прежних сериализованных состояниях; только запуск кода обновляется. Сбой любого из тестов или runtime проверок — блокер для релиза.
